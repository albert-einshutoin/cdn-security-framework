# 生成Workerの正常・不正リクエスト処理時間

対象HEAD: `1e0dc81c10c706697e33f5bb243cc783dba0c3aa`（PR #1110の生成ロジック）。製品ソースは変更せず、測定器と検証・結果を追加した。203ケース、182ケースのwarm分布、計874,442リクエストが成功。ここでの成功は、拒否を含め期待status・Origin到達数・本文/署名/レスポンス契約が一致したことを指す。

さらにGraphQL境界3ケースの同時負荷を対象限定で2回確認し、7,206リクエストが成功。合計881,648リクエスト。追加確認は主matrixの分布へ混ぜない。

## 測定条件

- Apple M4 / darwin arm64 / Node v24.2.0 / workerd 1.20261012.1、compatibility date 2026-07-20。
- 現在の生成器から出力したWorkerを既存esbuildで型消去し、native workerdで実行。生成JSの置換・fetchのモック・製品コードの計測用書換えはしない。
- Node HTTP client → loopback workerd → ローカルorigin → 応答本文読了までのwall time。クライアントのスケジューリング、HTTP、ログ処理、originの検証を含み、Worker単体CPU時間ではない。HMACケースはoriginで受信bytesからSHA256/HMACを独立再計算する。
- 同時1件を独立processで2回実行。各case/runで200 warmup + 1000計測、逐次列は2000 sampleをpool。同時16件も独立processで2回、各200 warmup + 1000計測、poolで2000 sample。負荷ケースの順序は固定で、同時負荷はclosed-loop。RPSはこの条件のthroughputで、サービス容量や本番SLAを示さない。各profileは同一workerd process内の別service/isolateで、対象外のserviceへリクエストを並行送信しない。
- 中央値・p95・p99はnearest-rank。最大値を含む全sampleをraw JSONへ保存し、外れ値を除外しない。first requestをwarmに混ぜない。
- first requestはケースの最初の1件であり、全行がfresh isolateではない。16個の専用JWKS serviceは独立cacheを持つfresh isolateだが、同じworkerd process内で測るため、本番cold startとは呼ばない。逐次32件の専用fresh測定はmedian 2.769ms、p95 4.529ms（小標本の記述値）。
- Geoはworkerdの`cfBlobHeader`で合成countryを注入。実PoPの国判定を実測したものではない。すべてのWorker outboundをloopback originへ固定し、ネットワークservice bindingは与えない。秘密値は合成fixtureのみ、RSA秘密鍵はメモリのみ。
- JWKS初回fetch数・測定全体fetch数・5秒のrefresh window内での完了、未知kid128種、空cacheへの同時要求、鍵更新・stale許容/拒否を検証する。拒否経路ではWorkerの理由ログとOrigin 0件も確認する。

JWKSが応答しない/本文が停止するケースは、初回が既存の約2000ms timeoutまで待つ。その後のnegative-cache hitだけを見て高速と判断しない。TTL 1秒の同kid鍵差し替えは、取得2回/5秒の予算との相互作用を避けず正しく扱うため、seed→1100ms待機→差し替え直後の1件を測る。反復してTTLが再失効すると別の拒否状態へ移るので、この遷移にwarm分布は付けない。安定したRS256 cacheの反復分布はjwks-okで測る。ブラウザ側のproof-of-work計算は含めない。

## 検証・失敗の扱い

- build:ts成功。測定器の5 tests成功（不正budget/selector、認証拒否と通過、DLP、cold並行JWKS、stale遷移）。本変更は測定器・テスト・文書のみで、製品の既存708件やhosted CIを今回再実行したとは主張しない。
- 全4runでstatus/本文/Origin到達数/JWKS取得数の期待値とcleanupが成功。生成policy・module・driver・source hashはrun間で一致し、現在sourceとも照合する。
- 初期の動作確認でcsp_nonce型・percent literalの現行挙動・query再serializeの期待値を修正。製品コードは変更していない。
- 最初の本測定は1秒TTLの鍵差し替えをwarm反復して再失効し、既存のrefresh budgetで401となったため失敗。rawをserial-initial-failed.jsonとして残し、最終4runへ混ぜない。buildの1回にSIGABRTがあり、同commandの次回は成功。原因は未特定で、成功扱いへ置換しない。
- レビュー初回はJWKS回数を記録のみとしていた点をBLOCK。期待fetch回数とwindow検証、cold並行ケース、回帰テストを追加した。最終Stop Review Gateの結果は別receiptへ記録する。

## 未測定・解釈の限界

- 全機能カテゴリの代表入力を測ったが、任意のPolicy/入力/組合せを全探索したものではない。最大値は観測最大であり上限保証ではない。
- managed Cloudflare/AWSのPoP・TLS・network・CPU、CloudFront native runtime、WAF managed rules/レート制限/IP reputation/JA3/JA4は未測定。JSでないprovider側処理はこのローカル値へ含めない。
- 任意のOrigin/JWKS network遅延、Origin接続失敗、slow-dripや長時間stream、open-loop飽和・長時間メモリ挙動、ブラウザproof計算は未測定。Originの接続/応答が遅い場合に全リクエストが同じ時間で完了するとは言えない。
- 逐次2回と同時16件2回は別の時間帯の観測。同時負荷の値には待ち行列とclient/originの負荷も含まれ、割合だけでWorker CPUの劣化と判断しない。

## 再実行

```sh
npm run build:ts
npx vitest run test/edge-security-benchmark.test.ts --maxWorkers=1
node scripts/benchmark-edge-security.js --output reports/edge-security-matrix-20261016/serial-1.json --samples 1000 --warmup 200 --concurrency 1
node scripts/benchmark-edge-security.js --output reports/edge-security-matrix-20261016/serial-2.json --samples 1000 --warmup 200 --concurrency 1
node scripts/benchmark-edge-security.js --output reports/edge-security-matrix-20261016/concurrent-16.json --samples 1000 --warmup 200 --concurrency 16
node scripts/benchmark-edge-security.js --output reports/edge-security-matrix-20261016/concurrent-16-repeat.json --samples 1000 --warmup 200 --concurrency 16
```

各commandを順に実行し、他のbuild/test/計測を重ねない。各runは最大10分、各HTTPは最大6秒、同時数は1..32、samplesは1..10000、warmupは0..2000。JWKS測定は5秒window内に収まらなければ失敗。`--only <case-id-prefix>`で部分選択でき、遷移に必要なseedは自動的に含める。warm cache前提のjwt-rs-bad-signatureは、jwks-okのprimeを含む完全matrixで測る。

[集計JSON](edge-security-latency-matrix.json)のrawReportsには全sampleを保存したローカルrawファイルのパス・SHA256・開始終了時刻・cleanupを記録。rawは既存reports/に保存し、秘密鍵・完全JWTは保存しない。
